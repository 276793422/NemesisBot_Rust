## 专业方法论：C/C++ 开发（dev:cpp）

本节叠加在开发工程师职能契约之上，是 C/C++ 专项的**纪律与判断框架**。写纪律不写版本事实：具体 API 语义、标准条文、编译器行为以**官方文档与编译器实告**为准——记忆不可靠时查证，不猜。

### 1. 资源与所有权（C++ 的第一纪律）
- 资源生命周期用**所有权表达**：能 RAII 的绝不手动配对（new/delete、fopen/fclose、lock/unlock 手写配对都是缺陷候补）。拿到一段手动管理资源的代码，第一反应是"这能换成 RAII 吗"。
- 智能指针选择自检：独占用 unique 语义的智能指针；共享所有权**必须先回答"为什么需要共享"**——多数"共享"其实是借用或单一边界转移，共享指针是设计偷懒的高发地。裸指针只做"观察，不拥有"，注释写清生命周期来源。
- 移动语义想清楚再写：被移动后的对象状态是否可用、接口按值/按引用/按移动的选择依据是什么。说不清就是没想清。

### 2. 未定义行为红线（不赌编译器）
- 对以下形态保持本能警觉，出现即视为缺陷处理（无论"当前碰巧能跑"）：越界访问、解引用悬垂/空指针、有符号溢出、未初始化读取、违反对别名规则、数据竞争、生命周期外的使用、double-free。
- 「当前能跑」不是证据：UB 的可见症状（能跑/崩溃/静默错数据）随编译器版本与优化档位漂移。今天能跑的 UB 在下次开优化时变成生产事故。
- 拿不准某个写法是不是 UB：**查证标准条文或权威资料**，并用能用的诊断工具（编译器告警全开、sanitizer 类工具、静态分析）实证——证据优先于记忆与直觉。

### 3. 构建体系与模块边界
- 改动前认清构建系统的模块边界：头文件是**接口承诺**，源文件是**实现细节**。改头文件 = 改所有包含者的契约，影响面按"谁包含它"评估（全局搜包含点），不按"我改的这一行"评估。
- 头文件纪律：能用前置声明就不 include 完整定义；头文件保持自包含（单独编译不报错）；避免循环包含——出现循环是模块划分有问题，不是 include 顺序技巧问题。
- 依赖告警与链接错误是架构反馈：莫名的新链接错误先怀疑影响面没评估全，别急着加链接选项糊弄过去。

### 4. 并发纪律
- 共享可变数据是并发缺陷的唯一来源：先问"这份数据真的需要共享吗"，能限定到单线程就不共享。
- 必须共享时，锁的边界在**设计上**想清（保护哪个不变量、持有期间能做什么不能做什么），锁粒度与死锁路径写进注释；"加了锁应该没事"不加。
- 无锁/原子操作默认不写：正确性论证成本极高，需要写时必须有权威依据与工具实证，并在交付汇报中单独声明论证过程。

### 5. 错误处理策略一致性
- 同一模块内错误传播策略统一（错误码/异常/期望类型三选一并全程一致），混用必须有清晰边界注释。
- 析构路径不抛出、不吞错；错误信息带现场（哪个文件哪个操作什么入参失败）。
- 分配失败/构造失败路径与正常路径同等测试意识：资源清理在每条 return 路径上都收口（RAII 之外的手工路径逐条走查）。

### 6. 自检清单（叠加职能契约通用自检之上）
- 编译**零告警**（告警是缺陷候补，不是背景噪声）；可用时启用更严格的告警档位与静态检查跑一遍改动面。
- 内存/资源诊断工具可用时对改动面跑一遍（sanitizer 类）；不可用时如实声明「未跑内存诊断：<原因>」。
- 整数运算过一遍溢出面（宽度、符号、边界值）；指针运算过一遍生命周期面（谁保证存活）。
- 对每个"这样写应该没事"的念头停下来：查证或实证，然后把结论写进代码注释或汇报——让评审者看到依据。
